机场配置改完就启用吗？先用 mihomo 本机校验，再验收真实连接

空空2026-11-03— 次阅读
排障与安全

从教程复制几行 DNS 或分流配置后，客户端突然启动失败，不一定是节点失效。先检查这份配置能否被当前内核解析，往往比立即更换订阅更容易定位。机场推荐教程里的可用示例，也需要结合你的内核和文件结构核对，不能照抄后直接替换原配置。

适用对象与准备

本文适用于已经使用 mihomo、能找到可信内核程序和本地配置的用户。图形客户端可能先合并订阅、覆写与脚本，再生成最终配置；只检查订阅原文，未必检查到了实际运行的内容。如果客户端提供配置校验入口，优先按其说明检查最终生效配置，不要随意修改软件内部文件。

先复制一份当前可用配置作为备份，再在另一份候选文件上编辑。记录内核版本、原配置名称、改了哪个字段和回退入口。完整配置可能含服务器密码、订阅链接或管理接口密钥，只保存在自己受控的位置，不贴进公开 YAML 检查网站。

示意图：先保留可用配置，再校验候选配置；解析通过后仍需检查实际连接与规则。

第一步：先看格式与层级

mihomo 官方语法说明指出，YAML 区分大小写，缩进应使用空格，同一层级要对齐。先查看错误所指行及前后几行，检查缩进、列表前的短横线、冒号后空格和成对引号。错误位置可能只是解析器无法继续的位置，真正原因可能在上一段。

每次只调整一组相关设置，再做一次检查。不要同时更换节点、DNS、规则文件和内核，否则即便恢复，也难以知道是哪项变化起作用。需要新增字段时，核对自己内核版本支持的官方文档；语法正确并不代表字段写在了正确位置。

第二步：让同一内核解析候选文件

官方源码定义 -t 为测试配置后退出，-f 指定配置文件。Windows 可在可信 mihomo 程序所在目录使用下面的形式，路径应换成自己的候选副本：

.\mihomo.exe -t -f ".\config-candidate.yaml"

若程序名称不同，按实际名称填写；macOS 或 Linux 按已安装程序的调用方式执行。不要为此下载陌生人打包的工具。看到成功提示后保留检查时间和内核版本；失败则记录错误、修正副本，再重复检查。校验可能涉及配置引用的外部资源和数据目录，不能把这一步宣称为完全离线的纯文本检查；遇到资源缺失或访问失败，应与缩进错误分开处理。

第三步：小范围启用与验收

配置解析成功只能证明本次解析未报错，不能证明每个节点可连、DNS 符合预期或规则方向正确。确认备份可恢复后，通过客户端正式入口启用候选配置，做三项小请求：打开可信网页、查看请求命中的规则和出口方向、完成一个自己需要的实际任务。不要用大流量测速代替这些核对。

如果启动成功但任务失败，保留该次日志，恢复原配置做同条件对照。原配置正常、候选配置异常，就从唯一改动处继续查；两者都失败，则另查本地网络、目标服务与账户状态。向客服提供内核版本、改动字段和脱敏错误即可，完整订阅与凭据不属于公开排障材料。

验收记录怎么写

建议写成“某版本内核在某时刻解析此候选文件成功，随后指定网页和规则验收通过，已保留原配置”。如果只完成 -t，就写“解析通过，连接待验收”。这能明确证据范围，也方便下次升级后复查，而不会把一次配置检查误写成长期稳定承诺。

可核验来源

  • mihomo 官方程序源码 main.go：-t、-f 参数及测试后的退出流程。
  • mihomo 官方 YAML 语法说明：大小写、空格缩进、对象与数组结构。
